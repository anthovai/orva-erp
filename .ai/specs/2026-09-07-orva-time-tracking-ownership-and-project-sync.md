# Time tracking ownership, and keeping โครงการ in step with โปรเจกต์

## 📝 TLDR

Orva shows the owner three screens that each call something a project: งาน
(`orva_tasking_projects` — the work), การเรียกเก็บตามโปรเจกต์ (`sales_quotes` —
the money, already tied to the work by a `quote_id`), and โครงการ
(`staff_time_projects` — the timesheet cost centre, holding zero rows). This
spec creates a new module, `orva_time`, which owns the mapping between a
tasking project and a time project and keeps the pair in step in both
directions, so hours are logged against the same projects the board and the
Gantt draw, and upstream's timesheet screens keep working unmodified.

It also answers Q-005 of `2026-09-06-orva-tasking-parity.md`, which put time
tracking in Non-goals precisely because the ownership question was open.

## 📝 Problem Statement

- `staff_time_projects` is empty while `orva_tasking_projects` holds 8 projects
  and 87 tasks. The owner opened โครงการ expecting to find the work there.
- `2026-09-04-orva-department-benchmark.md` (line 101) already committed to
  exposing `timesheets/projects → Projects`. That shipped in `20d7fa4`. What it
  never settled is where the rows come from.
- `2026-09-06-orva-tasking-parity.md` Non-goals: time tracking "belongs in its
  own spec, and `orva_hr` already owns staff, so the ownership question is real
  and should not be settled inside a tasking spec" (Q-005).
- Two tables holding the same project name is a drift surface, and the ask was
  explicitly "sync กันทั้งระบบ … ไม่มีบักหรือ error". Drift is therefore the
  thing this design is measured against, not a footnote.

## 📝 Decisions taken (the Open Questions, answered 2026-09-07)

| | Question | Answer |
|---|---|---|
| Q1 | Who owns the mapping | **A new `orva_time` module.** Not `orva_tasking` (the work should not have to know about staff), not `orva_hr` (which owns people, not the tasking↔timesheet seam) |
| Q2 | One-way or two-way | **Two-way** for a linked pair; a time project may also exist on its own |
| Q3 | Archiving a tasking project | Its time project becomes **`completed`**. Logged hours are never touched |
| Q4 | Which projects get a time project | **Every** tasking project, quotation or not (4 of 8 are งานภายใน) |
| Q5 | `code` | **Orva owns and locks it.** Generated by `orva_time`; read-only on a linked row |

**What "two-way" means here, stated so it can be corrected:** every tasking
project gets a time project (Q4), and for a *linked pair* an edit to the name,
status or colour on either screen propagates to the other. A time project
created by hand in โครงการ stays **standalone** — it is for work that is not a
tasking project at all, such as internal admin or leave, and does not
manufacture a tasking project. Two-way describes edit propagation, not
bidirectional creation.

## 📝 Proposed Solution

`orva_time` is a thin seam module: a link table, two sync directions, and a
reconcile command. It owns no domain of its own — the work stays in
`orva_tasking`, the hours stay in `staff`.

### Direction A — งาน → โครงการ (event-driven)

`orva_tasking` emits nothing today. It gains additive event definitions
(`events.ts` via `createModuleEvents()`; adding events is not a contract
change, so nothing existing moves) and emits them from the project routes:

- `orva_tasking.project.created`
- `orva_tasking.project.updated`
- `orva_tasking.project.archived`

An `orva_time` subscriber upserts the matching `staff_time_projects` row
post-commit. Effects stay outside the tasking transaction, per `AGENTS.md`.

### Direction B — โครงการ → งาน (API interceptor, and why)

`staff/events.ts` **declares** `staff.timesheets.time_project.created`,
`.updated` and `.deleted`, but nothing in the staff module ever emits them:
`api/timesheets/time-projects/route.ts` is a `makeCrudRoute` with no `events:`
config and no command backing, and no route in the whole staff module
configures `events:`. Verified by grep, not assumed. So the reverse direction
cannot be a subscriber.

It is an **API interceptor** instead. `makeCrudRoute` runs
`runApiInterceptorsBefore` / `runApiInterceptorsAfter`, so `orva_time`
registers an after-interceptor on the staff time-projects route that
propagates a rename or a status change back to the linked tasking project.
This is the designed extension point: no route replacement, no upstream edit.
(Orva does replace an upstream route elsewhere — `POST
/api/sales/document-numbers` — so the precedent for the heavier option exists
and is deliberately not used here.)

A **before**-interceptor on the same route rejects a `code` change on a linked
row, which is how Q5's lock is enforced server-side rather than only in the UI.

### Loop prevention

No "origin" flag, no suppression window. The link row stores the last values
the sync itself wrote (`synced_name`, `synced_status`); a propagation whose
target already holds the incoming value is a no-op. A → B → A therefore stops
at the second hop on value equality alone, which cannot be defeated by a lost
flag or a slow queue.

### Reconcile, because events are not enough

`mercato orva_time sync` (a CLI command, also runnable from a schedule):

- creates the missing time project for every unlinked tasking project — this
  is the backfill for the existing 8;
- repairs a pair whose `synced_*` values no longer match either side;
- reports links whose other end has been hard-deleted.

An event stream alone cannot fix a row missed while a worker was down. A sync
that is only ever event-driven is exactly the bug the owner asked to avoid.

### Alternatives rejected

| Alternative | Why it lost |
|---|---|
| Replace the โครงการ page with an Orva screen over `orva_tasking_projects` | Throws away upstream's KPI strip, saved views, hours sparkline and members — most of the page's value |
| Show only a work count on โครงการ, no sync | Offered and declined; also leaves hours unloggable against real projects |
| Hide โครงการ, put hours on the tasking project | Rebuilds a timesheet model `staff` already owns — forbidden by the reuse rules in `AGENTS.md` |
| Match rows by `code` instead of a link table | `code` is unique per org and user-editable upstream; an edit silently breaks the link. Q5 locks it, but a lock enforced by a table is stronger than one enforced by a convention |
| Put the link in `orva_tasking` | Makes the work module depend on staff; the tasking spec explicitly refused to settle this inside itself |

## 📝 Architecture

```
orva_tasking                 orva_time                      staff
────────────                 ─────────                      ─────
project write ──emits──▶  subscriber ──upsert──▶  staff_time_projects
                          orva_time_project_links
project update ◀──────  after-interceptor ◀──write──  time-project route
                          before-interceptor  ──reject code change
                          cli: sync (backfill + drift repair)
```

- No cross-module ORM relations. The link holds scalar ids and a `tenant_id`,
  and every read runs inside `withTenantRls`.
- `orva_time` depends on both module ids but on neither module's entities.
- The โครงการ and งาน pages are not rewritten. โครงการ gains its rows; งาน
  gains nothing visible in Phase 1.

## 📝 Data Model

### `orva_time_project_links` (new, owned by `orva_time`)

| Column | Type | Notes |
|---|---|---|
| `id` | uuid pk | `gen_random_uuid()` |
| `tenant_id` | uuid | RLS key |
| `organization_id` | uuid | |
| `tasking_project_id` | uuid | unique per tenant where `deleted_at is null` |
| `time_project_id` | uuid | unique per tenant where `deleted_at is null` |
| `synced_name` | text | last name the sync wrote; loop-breaker and drift oracle |
| `synced_status` | text | same, for status |
| `code` | text | the locked code `orva_time` generated |
| `created_at` / `updated_at` / `deleted_at` | timestamptz | |

Two unique indexes, so neither a tasking project nor a time project can be
linked twice. The migration ends with `select orva_apply_rls();` (CLAUDE.md).

No upstream table is altered. `staff_time_projects` is written through its own
API, never by reaching into its table.

### Field mapping

| tasking project | time project | On conflict |
|---|---|---|
| `name` | `name` | last write wins; the reconcile reports it |
| `isArchived: true` | `status: 'completed'` | Q3 |
| — | `code` | generated by `orva_time`, locked (Q5) |
| `quoteId` → quote → customer | `customer_id` | **Phase 2.** Resolving it needs a read across `sales`; out of Phase 1 rather than guessed at |
| — | `cost_center`, `owner_user_id`, `color`, `project_type` | left to the owner on the โครงการ screen; the sync never overwrites them |

## 📝 API Contracts

- `orva_tasking` project routes: unchanged request/response. They gain event
  emission only.
- New: `orva_tasking.project.created` / `.updated` / `.archived`, payload
  `{ id, tenantId, organizationId, name, isArchived, quoteId, updatedAt }`.
  Additive; no consumer exists to break.
- `staff` time-project routes: unchanged shape. A `code` change on a linked row
  now answers **409** with a message naming the tasking project that owns it.
- New CLI: `mercato orva_time sync [--dry-run]`. `--dry-run` reports and writes
  nothing — the importer's dry run shipped a bug where it reported zeros as
  findings (`afcf17e`), so this one is tested for it.

## 📝 Edge Cases & Failure Scenarios

| Case | Behaviour |
|---|---|
| Time project renamed while the tasking project is renamed in the same minute | Last write wins; `synced_name` no longer matches either, so `sync` reports the pair as drifted rather than silently picking |
| Subscriber fails (worker down) | Link is absent; `sync` creates it on the next run. The owner sees โครงการ missing a row, never a wrong row |
| Tasking project hard-deleted | Link soft-deleted, time project moved to `completed`, hours kept. Nothing is destroyed on the hours side, ever |
| Someone edits `code` on a linked row | 409 before the write, naming the owning project |
| Standalone time project (leave, admin) | No link, never touched by the sync |
| Two organizations, same project name | Link is scoped by `tenant_id` + `organization_id`; the unique indexes are per tenant |
| RLS: subscriber runs without a tenant GUC | `withTenantRls` sets it; a subscriber that cannot resolve a tenant fails loudly instead of writing across tenants |

## 📝 Risks & Impact Review

- **Blast radius**: one new table, one new module, event emission added to two
  tasking routes, two interceptors on one upstream route. No upstream schema
  change and no upstream file edited.
- **Rollback**: remove `orva_time` from `src/modules.ts`. The link table is
  then inert; `staff_time_projects` rows and all logged hours stay. Tasking
  keeps emitting events nobody listens to, which is harmless.
- **Migration**: additive, one table, no backfill inside the migration. The
  backfill is the CLI, so it is re-runnable and reviewable.
- **The thing most likely to go wrong**: the two-way propagation. It is why the
  loop-breaker is value equality rather than a flag, and why `sync` reports
  drift instead of resolving it silently.

## 📋 Phasing

**Phase 1 — one direction, and the rows exist. SHIPPED (5932ec9).** `orva_time` module skeleton,
the link table and its migration, the three tasking events, the subscriber, and
`mercato orva_time sync` with the backfill for the existing 8. โครงการ shows 8
rows. Integration test: create a tasking project → a time project appears with
the generated code; run `sync` twice → no duplicates.

**Phase 2 — the other direction, and the lock. SHIPPED.** The after-interceptor
(rename/status back to tasking), the before-interceptor (409 on a `code`
change), drift reporting in `sync`, and `customer_id` resolved from the
quotation. Integration test: rename on each screen, assert the other follows
and that the loop stops.

**Phase 3 — hours where the work is. NOT STARTED.** Surface logged hours on the งาน project
card beside งาน% and เรียกเก็บ%, which is the pairing `orva_tasking`'s spec
exists for. Read-only; no new writes.

Each phase leaves the application working. Phase 1 alone answers the owner's
original complaint.
